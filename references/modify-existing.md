# 修改与重构已有项目

当任务是对已有页面、组件或项目进行修改、优化、重构、修复或适配时读取本文件。此时不是从空白画布设计，而是先提取现状，再在现有系统内做最小正确改动。**默认保留现有视觉语言，只在任务要求的范围内改变；更换视觉语言必须由用户明确要求。**

## 核心原则

1. 默认保留现有视觉语言，只在任务要求的范围内改变。
2. 先提取现状，再判断改动；不理解现状就动手等于重新设计。
3. 只修改与任务相关的内容，不借机重建整个界面。
4. 改完后与相邻页面保持一致，不让项目出现两套语言。
5. 修复要定位根因：是系统的样式缺陷还是单页实例问题；系统问题改 token，实例问题才改局部。

## 第一步：提取现状

改动前从代码、样式和已有页面中提取当前项目的视觉语言，至少覆盖：

| 维度 | 要提取什么 |
| --- | --- |
| 设计变量 | CSS 变量 / token：主色、辅助色、语义色、字体栈、字号、间距、圆角、阴影 |
| 组件库 | 已有组件及其默认外观、用法约定 |
| 排版 | 标题层级、字号关系、字重、行高、正文字号 |
| 间距节奏 | 区块间距、内容组间距、常用留白值 |
| 形状与材质 | 圆角半径、阴影强度、边框/分割线用法、背景材质 |
| 密度 | 首屏信息量、扫描速度、区块高度 |
| 动效 | 过渡时长、缓动、进入/退出方式、hover 反馈 |
| 页面职责 | 当前页面在导航中的位置、与相邻页面的关系 |

提取后形成一行结论：`当前项目视觉语言 = [各维度简写]，本任务只触碰其中 [改动维度]。`

## 第二步：任务分流

判断任务的改动等级，不同等级使用不同约束：

| 等级 | 定义 | 做法 |
| --- | --- | --- |
| 修复 | 某处效果、行为或状态不符合预期 | 在现有视觉语言内修正，不更换语言 |
| 微调 | 局部布局、间距、配色或内容的调整 | 只改目标区域，其他保持不动 |
| 重构 | 结构或实现重组，视觉不变或轻微变化 | 复用现有 token/组件，优先改样式而非重写结构 |
| 重塑 | 用户明确要求整个页面/项目换一种视觉风格 | 才走「从零设计」流程（三个剪影、气质维度、产品指纹） |

**用户没有明确说「换风格 / 重塑 / 重新设计」时，一律按前三级处理，禁止更换视觉语言。**

## 第三步：最小改动

- 改动顺序：能改设计变量（token）就不改组件；能改组件就不改页面结构；能不动的代码一律不动。
- 新值从现有系统中派生：需要新颜色时从现有色板扩展，需要新字号时进入现有字号阶梯；不引入孤立的色值、字号、圆角或阴影。
- 保持一致性：圆角、阴影、密度、动效与相邻页面使用同一套参数；不因为本页面好看就给项目加第二套语言。
- 明确不动的部分：记录哪些代码、布局和视觉元素是特意保留的，防止把「顺手改掉」当成「优化」。
- 修复时定位根因：同样的缺陷出现在多个页面时改共用 token/组件，而不是逐个页面打补丁。
- 不借机重构：任务范围内明显冲突的地方可以提示用户，但默认不做无关重构。

## 第四步：前后对比验证

改动完成后逐项确认：

- **范围**：diff 中每一处改动都能对应任务需求，没有无关改动。
- **相邻页面**：共用组件、全局样式、token 未被无意改动。
- **风格一致**：复用「风格距离」检查，逐项比较骨架、排版、色彩、形状、材质、密度，确认没有引入新语言。
- **自洽**：新增元素能从现有 token 派生，不出现孤立色值/字号/圆角。
- **目标达成**：回到任务描述，确认被提出的问题或优化目标已解决，而不是「看起来不同了」。

## 交付说明

- 明确列出：改了什么、保留了什么、为什么保留。
- 说明改动是在现有系统内完成的，新增 token 与旧值的关系。
- 如果本可以更省事（例如只改一个 token）却改了很多文件，说明原因。
- 如果改动会同时影响其他页面，先说明影响面再动手。
