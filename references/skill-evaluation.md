# Skill 验证协议

仅在改进 NiceUI 本身、并使用页面或组件作为验证样本时读取本文件。

## 区分目标与样本

- NiceUI Skill 是正式目标；HTML、React 页面、截图或临时项目是验证样本。
- 样本用于暴露规则是否可执行、是否遗漏门禁以及是否会过拟合，不定义 NiceUI 的固定品牌或默认页面。
- 不把样本的产品名称、布局、颜色、文案和组件写回 NiceUI 默认值。
- 不因样本难看而只修饰样本；先定位是路由、内容、构图、视觉、交互还是验证规则失效。

## 迭代顺序

1. **记录失败**：使用可观察描述，例如“官网被做成后台”“结构依赖 22 处边框”“页面充满设计说明”，不要只写“不好看”。
2. **定位层级**：判断问题属于核心原则、条件路由、详细参考还是验证清单。
3. **修改 Skill**：加入最小但可泛化的判断、流程或门禁，避免针对当前样本写固定模板。
4. **重新验证**：从原始任务重新运行样本，不把预期答案或上一版页面当作必须保留的结构。
5. **审查迁移性**：确认新规则不会只适合官网，也不会破坏博客、后台、商店、作品集、文档或工具。

## 验证矩阵

不要用一个页面证明 NiceUI 已经稳定。逐步覆盖：

- 官网：首页主张、真实产品证据和行动路径。
- 博客：首页发现与文章详情阅读。
- 后台：列表扫描、状态、筛选和批量操作。
- 商店：商品判断、规格、库存与购买。
- 工具：打开后直接操作工作对象。

每次不必全部重做；选择与本轮改动最相关的两个不同类型进行验证。无法启动独立验证线程时，至少使用两个互不相关的任务简报进行静态路由检查。

涉及风格同质化时，验证样本必须覆盖至少一个展示型页面和一个高频业务页面。并排检查骨架、排版、色彩、形状、边界材质、图像、控件、时间节奏、密度与记忆点；仅换色或换布局不算通过。

## 失败门禁

出现以下任一情况时，不把样本判为通过：

- 页面类型或职责判断错误。
- 页面展示设计过程、批注或面向评审者的说明。
- 换名后可以无损变成完全不同的产品。
- 超大标题、空白、卡片或边框承担了主要层级。
- 任何文字的计算字号超过 `22px`。
- 参考图被整页复刻，或多个参考被平均成固定风格。
- 不同页面反复使用相同字体组合、暖灰或低饱和表面、小号等宽眉题、居中限宽、柔和圆角和轻微悬停，导致产品类型不同但仍像同一本杂志。
- 主要控件没有真实行为。
- 只检查语法、溢出和控制台，没有进行视觉门禁。

## 样本处置

- 将验证样本视为可替换工件，不把它放入 Skill 的 `assets/` 作为默认模板。
- 用户没有要求交付样本时，不围绕样本持续扩展功能。
- 验证完成后只汇报它证明或暴露的规则问题；NiceUI 的改动才是主要交付。
